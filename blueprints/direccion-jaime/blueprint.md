## 1. Project Overview & Non-Goals

### Vision

Hoy Improvement le enseña al dueño de una empresa cliente **qué** le falta (necesidades), **quién**
hace qué (objetivos con puntos) y **cómo va** (el panel de Indicadores). Lo que no tiene es el ritmo
con el que una empresa chica se dirige a sí misma cada semana: una visión escrita que todos leen, un
puñado de números que cada responsable captura los lunes, una lista de problemas que se discuten hasta
resolverse y una junta semanal de 90 minutos que amarra todo eso. Ese ritmo es lo que Ninety.io vende
sobre EOS, y es lo primero que Jaime Salinas (Camibel) necesita para dejar de dirigir de memoria.

Este cambio agrega a `apps/improvement` cuatro módulos — **V/TO**, **Scorecard semanal**, **Issues
(IDS)** y **Junta L10** — bajo `/[org]/direccion`, construidos sobre el motor genérico que ya existe:
los issues **son** las filas de `org_need`, los pendientes **son** `objective` creados por la misma
función de siempre, y quién ve cada módulo lo decide el dueño con los tipos de permiso que ya maneja.
Nada de Camibel vive en código: su visión, sus medibles y sus juntas son filas.

### Goals — v1 scope

1. El dueño escribe y edita una V/TO de seis secciones por empresa; quien tenga la sección `vision` la lee.
2. El equipo captura un valor por medible por semana (lunes, America/Mexico_City) y ve 13 semanas con
   "En meta"/"Fuera de meta" en texto y color.
3. Los issues de la empresa se mueven por IDS (`abierta` → `en_progreso` → `resuelta`) con responsable,
   lista prioritaria de la semana y pendientes que nacen como objetivos.
4. Una junta L10 de 7 bloques (90 min) se corre en un solo dispositivo, lee en vivo scorecard, objetivos
   e issues, y se cierra con calificaciones y promedio.
5. El dueño decide, por tipo de permiso, quién ve cada uno de los cuatro módulos.

## 2. Tech Stack

**Runtime track: ts-node, tal como ya está en el repo.** Este cambio **no agrega ni actualiza ninguna
dependencia**. Las versiones viven en §11 y en `pnpm-lock.yaml`.

| Layer | Choice | Why this, over what |
|---|---|---|
| Language / runtime | TypeScript 6 sobre Node 24 (ya en el repo) | Es lo que corre `apps/improvement`; un segundo lenguaje no cabe en un cambio de 12 pasos |

| Component layer | Componentes propios del repo, sin librería nueva | Una librería de componentes para 5 pantallas es más superficie que código |
| Database | Postgres del Supabase compartido (ya en el repo) | No hay base local; el repo ya prueba contra el proyecto real |
| ORM / data access | Drizzle 0.45 (`packages/db`), migraciones por `drizzle-kit` | Fuente única `packages/db/src/schema.ts`; una segunda forma de migrar está prohibida |
| Auth | Supabase Auth + `server/auth/guard.ts` (ya en el repo) | `requireSection` ya resuelve sección + alcance; no hay nada que agregar |
| Background work | NOT APPLICABLE — ningún módulo de Dirección corre fuera de una request | — |
| Payments | NOT APPLICABLE — Dirección no cobra | — |
| File storage | NOT APPLICABLE — Dirección no sube archivos | — |
| Email / notifications | NOT APPLICABLE en v1 — el aviso de junta pendiente es la tarjeta en la recepción | Un correo de recordatorio llega con `server/reminders` si la tarjeta no basta |
| Hosting | Vercel (ya en el repo) | Sin cambios de infraestructura |
| Package manager | pnpm 11.24.0 (`packageManager` en `package.json`) | Lo fija el repo |

### Compatibility check

Checked against `knowledge/stack-compatibility.md`. La combinación ya en producción en este repo usa
**Supabase Auth + base de Supabase** (la fila "Lean SaaS": un solo dueño de sesión, sin Clerk), que el
archivo permite siempre que no corran dos proveedores de identidad — no corren. El riesgo de "dos
sistemas de migración sobre una base" se evita con la regla del repo: el editor del dashboard de
Supabase es solo lectura y `packages/db/migrations/` es la única fuente. No known-bad combinations.

## 5. API Design

### Conventions

- Base path: no hay rutas HTTP nuevas. Toda lectura es un Server Component que llama a `server/direccion/**`; toda escritura es una Server Action inline (`async function x(formData) { "use server"; … }`) dentro del `page.tsx`, que resuelve el actor con `getSessionUserId()` y llama a `server/direccion/**`.
- Response envelope: `type Result<T> = { ok: true; data: T } | { ok: false; error: { code: string; message: string } }` — el mismo de `server/needs/mutations.ts`. Las lecturas devuelven el dato o una vista vacía; nunca lanzan, salvo el `notFound()` de `assertMembership` para un no-miembro.
- Error codes: `FORBIDDEN` (alcance o rol insuficiente), `VALIDATION_ERROR` (zod), `NOT_FOUND` (id ajeno al org), `INVALID_TRANSITION` (IDS), `ALREADY_STARTED`, `NOT_STARTED`, `LAST_BLOCK`, `NOT_READY`, `ALREADY_ENDED`, `DB_ERROR`. La Server Action convierte `ok: false` en `redirect(`${pagina}?error=${encodeURIComponent(message)}`)`, como `necesidades/page.tsx`.
- Validation: zod 4, en cada función de `server/direccion/**` que recibe `input: unknown`, en el mismo archivo.
- Pagination: NOT APPLICABLE en v1 — 13 semanas fijas, juntas: las últimas 10, issues: los no derivados de un org (decenas).
- Idempotency: el upsert de `measurable_value` (único por medible+semana) y de `meeting_rating` (único por junta+persona) hace idempotente la recaptura; `startMeeting` falla con `ALREADY_STARTED`.
- Rate limits: NOT APPLICABLE — sin endpoints públicos; todo pasa por sesión + sección.

Reglas que se vuelven criterios en §9:

- **`weekStart`** formatea `now` con `Intl.DateTimeFormat("en-US", { timeZone: "America/Mexico_City", year: "numeric", month: "2-digit", day: "2-digit", weekday: "short" })`, toma año/mes/día/día-de-semana de `formatToParts`, construye esa fecha en UTC y le resta los días desde el lunes. Nunca usa `getDay()` de la hora del servidor. Implementación de referencia (ejecutada en Node 24.19.0, ver §19.6 *Byte-exact*):

  ```ts
  const OFFSET: Record<string, number> = { Mon: 0, Tue: 1, Wed: 2, Thu: 3, Fri: 4, Sat: 5, Sun: 6 };
  const FMT = new Intl.DateTimeFormat("en-US", {
    timeZone: "America/Mexico_City", year: "numeric", month: "2-digit", day: "2-digit", weekday: "short",
  });
  export function weekStart(now: Date): string {
    const p = Object.fromEntries(FMT.formatToParts(now).map((x) => [x.type, x.value]));
    const d = new Date(Date.UTC(Number(p.year), Number(p.month) - 1, Number(p.day)));
    d.setUTCDate(d.getUTCDate() - (OFFSET[p.weekday ?? "Mon"] ?? 0));
    return d.toISOString().slice(0, 10);
  }
  ```

## 8. Authentication & Authorization

### Provider and rationale

Supabase Auth + `server/auth/guard.ts`, sin cambios. Dirección solo agrega secciones al mecanismo que
ya existe.

### Flows

Sin flujos nuevos de sesión. Recorrido de autorización de cualquier ruta de Dirección:

1. Sin cookie `imp-access-token` válida → `requireSection` → `requireOrgMembership` → 404.
2. Con sesión pero sin membresía en `[org]` → 404.
3. Con membresía y alcance `ninguno` en la sección → 404 (`requireSection`).
4. Con alcance → la página carga; cada función de `server/direccion/**` vuelve a resolver el alcance
   adentro y filtra (`propio`) o rechaza (`FORBIDDEN`) — la pantalla escondiendo un botón no es permiso.

### Route protection

| Surface | Rule | Enforced where |
|---|---|---|
| `/[org]/direccion` | miembro + ≥1 de las 4 secciones | `app/[org]/direccion/page.tsx` (`requireOrgMembership` + `loadDireccionNav`, vacío → `notFound()`) |
| `/[org]/direccion/vision` | sección `vision` | `vision/page.tsx` → `requireSection(orgId, "vision")` |
| `/[org]/direccion/scorecard` | sección `scorecard` | `scorecard/page.tsx` → `requireSection(orgId, "scorecard")` |
| `/[org]/direccion/issues` | sección `issues` | `issues/page.tsx` → `requireSection(orgId, "issues")` |
| `/[org]/direccion/junta` | sección `junta` | `junta/page.tsx` → `requireSection(orgId, "junta")` |
| Escrituras solo-dueño | `membership.role = 'owner'` | `findOwnerMembership` en `vision.ts`, `measurables.ts`, `issues.ts`; `createObjective()` para pendientes |

**Enforcement rule:** authorization is checked server-side on every request. Client-side route
guards are cosmetic and never the only check. A hidden button is not a permission.

### Roles and permissions

| Role | Can | Cannot |
|---|---|---|
| Dueño (`role = owner`) | Todo en las cuatro secciones: editar V/TO, definir/archivar medibles, capturar cualquier valor, crear issues y pendientes, mover/priorizar/asignar issues, crear y cerrar juntas | — |
| Empleado `vision: empresa` | Leer la V/TO | Editarla |
| Empleado `scorecard: empresa` | Ver todos los medibles y capturar en cualquiera | Definir o archivar medibles |
| Empleado `scorecard: propio` | Ver y capturar solo los medibles de los que es responsable | Ver los de otros |
| Empleado `issues: empresa` | Ver todos los issues; moverlos, priorizarlos, asignar responsable | Crear issues o pendientes |

| Empleado `junta: empresa` | Crear, iniciar, avanzar, anotar, calificar y cerrar juntas | Crear pendientes (los crea el dueño) |
| Sin la sección (`ninguno`, o sin tipo) | — | Ver la ruta (404) |

`responsibility_level` no aparece en ninguna lectura de Dirección (Non-negotiable #4 intacto):
`listTeammates` ya lo omite.

### Sessions

Sin cambios: cookie `imp-access-token` con el access token de Supabase, leída por `getSessionUserId()`.

### Multi-tenancy / row-level isolation

Dos puertas, dos cerraduras, ninguna respalda a la otra (ver `CLAUDE.md`, *Dos puertas*):

| Camino | Quién conecta | Única autorización para Dirección |
|---|---|---|

Una función nueva de `server/direccion/**` sin `resolveSection` fuga por la primera puerta; una tabla
